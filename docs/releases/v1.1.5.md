# Space Data Network v1.1.5

Space Data Network 1.1.5 is the node as on `main` at the tag `v1.1.5`. It replaces v1.1.4 as the release to download.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. A node with default settings acts on update signals it hears on the network. A signal signed with that key can make such a node download and run a program from any HTTPS address. 1.1.4 and 1.1.5 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced yet.

## What is in it beyond 1.1.4

- **Linux: a fresh node gets its key password file.** On most Linux machines a node that does not run as root could not start for the first time until the operator made a password file by hand. The installers, the packages and the container now make it for a fresh node. The section "Linux key password file" below has the details, including where the file is kept and what a copy of the node's data opens.
- **The dashboard shows the node's version.** The bottom of the left menu says "SDN" over the version, and the whole block is one link to that release's notes. A build that is not a release says so ("1.1.5 dev") and links to the releases list. When the node does not answer, the block says "version unavailable" and reads again by itself.
- **`/admin` opens the dashboard.** Every page address under `/admin` goes to the dashboard at `/`, so the older admin pages cannot be reached from a browser. The admin UI's own files and API routes answer as before, behind the same sign-in.
- **FlatSQL 3.12.5.** A statement that looks up many rowids spread over a large type (`_rowid IN (...)`, or an OR of `_rowid =` terms) is answered: sixteen rowids spread over 150,000 records failed with "reader cursor failed" before. SQLite's math functions (`pow`, `sqrt`, `sin`, `atan2`, `ln`, `log10`, `exp`, `pi`, `degrees` and the rest) are built in. The store format is unchanged. Each node compiles the new engine once, at its first start or ahead of it with `spacedatanetwork prewarm-aot`.
- **Converting a legacy store.** `spacedatanetwork store-migrate --to 5` on a format-1 store no longer refuses to activate because old index rows lack an epoch. Builds from before 2026-09-26 gave an MPE record whose epoch lies before 1970 no index epoch. The check now compares format 5's epoch with what the index rule gives for the record's bytes, counts such records in its report (`epochs_format1_lacked`), and still refuses any record where the two differ.
- **Packages.** The Linux packages ship the wallet module the command line loads for its key backup commands.

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.5` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit.

## Updating an installed node

- **From 1.1.4,** run `spacedatanetwork update install`. The release channel at `https://sdn.spaceaware.io/updates` serves this release (published there 2026-11-16). The command fetches the signed update and verifies it against the bundle's update root; a helper then stops the running node, swaps the bundle, starts the node and waits for it to answer ready. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Replacing the binary by hand works as before: stop the node, install the 1.1.5 download or package in place of the old one (keep `keys/` and the config), and start the node. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **From 1.1.0 or earlier,** update by hand, because the updater in those releases reverts the updates it drives itself: stop the node, install the 1.1.5 download or package in place of the old binary (keep `keys/` and the config), and start the node. A format-4 store converts at the first start; the v1.1.4 release notes give the disk it needs and how long it takes.
- **The first start** compiles the new storage engine once, about a minute and a half on a 4-CPU machine; `spacedatanetwork prewarm-aot` does that before the restart.

**macOS desktop app.** Not in this release; the macOS command-line downloads (Apple silicon and Intel) are.

## Linux key password file

**Linux: a fresh node gets its key password file automatically.** The Linux
kernel makes `/sys/class/dmi/id/product_uuid` readable only by root, so on
most Linux machines a node that does not run as root cannot derive its
key-at-rest password from the machine. Before this release such a node
refused its first start until the operator made a password file by hand. Now
the installers do it for a fresh node: no identity yet, no `SDN_KEY_PASSWORD`
or `SDN_KEY_PASSWORD_FILE` and no key password in the config, and a machine
fingerprint that is refused for the node's account (`spacedatanetwork key
fingerprint-check` says `ok`, `absent` or `refused`). The file holds 32 random
bytes as 64 hex characters, mode 0400, owned by the node's account, and is
never overwritten. **Keep it for the life of the node: the node cannot open its
identity without it.** Where it is kept decides what a copy of the node's
data opens:

- `install.sh` as a regular user: `~/sdn-key-password`, outside
  `~/.spacedatanetwork`, recorded in the node's config as
  `security.key_password_file`, so every later start and every CLI command
  finds it with nothing exported. A copy of `~/.spacedatanetwork` alone does
  not open the identity; back the file up apart from it.
- `.deb` / `.rpm`: `/var/lib/spacedatanetwork/key-password` (`sdn:sdn`, the
  path of the v1.1.0 recipe) and the drop-in
  `/etc/systemd/system/spacedatanetwork.service.d/key-password.conf` that sets
  `SDN_KEY_PASSWORD_FILE` for the service. **The file is in the data
  directory: a copy of `/var/lib/spacedatanetwork` alone opens the node
  identity and its credential store.** Move it (and change the drop-in) to
  keep them apart. CLI commands need the variable too: `sudo -u sdn env
  SDN_KEY_PASSWORD_FILE=/var/lib/spacedatanetwork/key-password
  /opt/spacedatanetwork/bin/spacedatanetwork -c
  /etc/spacedatanetwork/config.yaml <command>`. The file is made at package
  install, so a machine image built with the package installed gives every
  clone one password: remove the file and the drop-in on each clone and
  reinstall the package before its first start. Removing or purging the
  package leaves both, like the identity.
- Container (uid 1000): `/app/data/key-password`. **It is in the data volume:
  a copy of the volume alone opens the node identity and its credential
  store.** A password file mounted from outside the volume with
  `SDN_KEY_PASSWORD_FILE` keeps them apart, and the entrypoint then generates
  nothing; that remains the recommended setup. Nothing is generated when the
  config keeps the key directory outside `/app/data`. `docker exec` does not
  pass through the entrypoint, so run CLI commands as `docker exec <container>
  /app/entrypoint.sh <command>`, for example `show-identity --config
  /app/config/full-docker.yaml --show-mnemonic`.

A node that already has an identity is not touched by an upgrade (its
identity stays sealed exactly as it is), and a node running as root, on macOS
or on Windows needs no file. A command refused on such a node now names the
generated file and the command line that passes it, and a first start that is
still refused says that no identity exists yet, why this host's fingerprint is
refused, and how to proceed, instead of saying a secret failed to open.

**The credential store follows the identity's key password.** It now uses
`SDN_KEY_PASSWORD`, `SDN_KEY_PASSWORD_FILE`, `security.key_password`,
`security.key_password_file`, in that order, so "credential store
unavailable" no longer appears on nodes whose identity needs a password file.
A store that an earlier release sealed under the machine key while the
node's password was in a file stays sealed that way and keeps opening, so a
rollback still opens it; only where the machine key is now refused is it
re-sealed under the password. A store this release CREATES on a node with a
key password file is sealed under that password, and an earlier release
(after a rollback, or the update helper's automatic revert) reports
"credential store unavailable" for it until the node runs this release again.

**CLI config discovery ignores other accounts' processes.** A CLI command
given no `-c` and no `SDN_CONFIG` used to take its config from any running
process whose command line read `spacedatanetwork daemon --config ...`,
whoever ran it, so another local account could choose the config that
`init` loaded and saved. Only a daemon run by the same account, by root or by
a system account (such as the package's `sdn`) counts now; for another
account's node, pass `-c`. `install.sh` passes the node's own config to every
command it runs.
