# Space Data Network v1.1.6

Space Data Network 1.1.6 is the node as on `main` at the tag `v1.1.6`. It replaces v1.1.5 as the release to download.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. A node with default settings acts on update signals it hears on the network. A signal signed with that key can make such a node download and run a program from any HTTPS address. 1.1.4, 1.1.5 and 1.1.6 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced yet.

## What is in it beyond 1.1.5

- **Full-text search finds every record.** A record stored with its FlatBuffer size prefix was kept intact but never found by full-text search. Records arrive that way over libp2p data-push and pubsub, from a module's storage write, and when the node builds a record itself. FlatSQL 3.12.6 indexes them. An index built by an earlier release repairs itself at the first start: no reindex command is needed. While the repair runs, a search answers 503 `search_index_building` with a retry hint. Stored bytes, content addresses, the store format and the wire formats are unchanged.
- **Built with Go 1.26.11.** 1.1.5 was built with Go 1.26.8, which has nine known defects in its standard library that reach a node's public listeners: in the HTTP/2 and HTTP/1 servers, in TLS, in X.509 certificate parsing, in header parsing and in HTML templates. They are fixed in Go 1.26.9 through 1.26.11. The command-line builds, the packages and the container image are all built with 1.26.11.
- **The dashboard runs the storage engine's own browser runtime.** The embedded dashboard loads the same engine file the node uses, through its browser runtime, under the same content security policy (no `unsafe-eval`). The dashboard page is larger for it: 28 MB against 11 MB, sent uncompressed by the node.
- **Rebuilding the search index waits until it is complete.** `spacedatanetwork reindex` returns when the index is built, not when the rebuild is accepted.
- **Dependencies.** `google.golang.org/grpc` is at the version the linked Kubo 0.43.1 builds with.
- **macOS desktop app.** In this release, for Apple silicon and Intel, signed and notarized.

**Downloads.** Installers and archives for macOS, Linux and Windows, the macOS desktop app, the container image `dockerdigitalarsenal/space-data-network:v1.1.6` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit.

## Updating an installed node

- **From 1.1.4 or 1.1.5,** run `spacedatanetwork update install`. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The command fetches the signed update and verifies it against the bundle's update root; a helper then stops the running node, swaps the bundle, starts the node and waits for it to answer ready. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Replacing the binary by hand works as before: stop the node, install the 1.1.6 download or package in place of the old one (keep `keys/` and the config), and start the node. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **From 1.1.0 or earlier,** update by hand, because the updater in those releases reverts the updates it drives itself: stop the node, install the 1.1.6 download or package in place of the old binary (keep `keys/` and the config), and start the node. A format-4 store converts at the first start; the v1.1.4 release notes give the disk it needs and how long it takes.
- **The first start** compiles the new storage engine once, about a minute and a half on a 4-CPU machine; `spacedatanetwork prewarm-aot` does that before the restart. It also repairs the full-text index in the background, as described above.

## Linux key password file

A fresh node on Linux gets its key password file from the installers, the packages and the container, as since 1.1.5. The v1.1.5 release notes say where the file is kept for each kind of install and what a copy of the node's data opens.
