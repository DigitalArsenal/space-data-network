# Space Data Network v1.1.7

Space Data Network 1.1.7 is the node as on `main` at the tag `v1.1.7`. It replaces v1.1.6 as the release to download.

## Compatibility: nodes that exchange publications update together

**A node on a build older than 1.1.6 does not accept publications signed by 1.1.6 or later, 1.1.7 included.** The signed dataset manifest names its index as a PublicationState file (`*.index.fb`), and the signed feed-head frame carries two more columns; an older node refuses both. Nodes that exchange publications must all run 1.1.6 or later: update them together.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. A node with default settings acts on update signals it hears on the network. A signal signed with that key can make such a node download and run a program from any HTTPS address. 1.1.4 through 1.1.7 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced.

## What is in it beyond 1.1.6

- **Updates by push, with an automatic return to the previous build.** The release pipeline signs an update signal beside the update feed. A node with the signal lane on (the default, `update.enabled`) acts on a signal only when it is signed by a trusted update key and points into the node's own update feed; it then fetches the signed update, and the update helper stops the node, swaps the bundle, starts it and waits for it to answer ready. A build that does not answer ready in time is replaced by the previous build and quarantined, so the node is back on the build it ran before. A node that missed a signal catches up from the feed, a signed withdrawal stops a release from being installed, and the update topics carry only messages that pass a validator. A hand-off that fails after the node was stopped keeps its backoff across the restart instead of stopping and restarting the node every few minutes.
- **The runtime self-test gives the same verdict under load.** A self-test that cannot decide (a probe that timed out on a busy machine) is run again, up to three runs, and a timed-out probe is repeated until it decides. An undecided self-test no longer turns store format 5 off for the life of the process, never creates a new store in the old format, and loads no compiled artifact another runtime made.
- **FlatSQL 3.12.10: a lane of over a million objects keeps every record over a restart.** Past 1,000,000 object keys, a feed's merged dictionary segment was refused on reading, and the next open cut the stream at that segment, dropping the records written after it. The engine also returns an error, starting nothing, when it cannot create one of its threads, instead of aborting. The store format is unchanged.
- **Streaming between nodes.** A node follows a lane from its producer over one stream: the producer states the lane's current batch, the follower fetches what it lacks and makes a batch current only once it holds every listed record, and records of other producers in the lane stay. Publishing and exporting a lane takes time in proportion to its size: its fingerprint and its windows are read by key instead of by offset, so a window no longer re-reads every record before it, and a receiver imports a shard up to 4,096 records per engine write instead of 64 (2,000,000 element sets: first announcement to all readable on the receiver in about 90 s, against 390 to 520 s). A lane's count comes from the lane's counters in microseconds instead of a read of every record, and a lane's stream figures (followers, records and bytes received and served, rates) fill its `$DSS` record on both sides. Hardening: a lane is followed only from a trusted peer and only as the node's import policy admits, checked at every page; every frame is verified before it is read; pages and their headers are bounded and checked before anything is allocated; a fault in one stream ends that stream and never the node; and a producer serves a bounded number of streams to each peer. The per-record push message of the exchange protocol, which no release sent, is removed and refused as an unknown message. Catch-up from a peer lists every standard within the peer's rate limit, resuming where the last pass was refused.
- **Writes wait for a running compaction.** A write that needs room while the store compacts in the background waits for that compaction instead of being refused.
- **Module SDK 0.10.4 and Space Data Standards 1.284.0.** The module SDK carries the browser thread-pool fix of 0.10.3. The standards add, among others, the rocket-equation mass fields of `$MPL` (`INITIAL_MASS_KG`, `SPECIFIC_IMPULSE_S`), the stream figures of `$DSS` and following in `$QRP`.
- **Host roll script.** `deployment/scripts/roll-to-format5.sh` replaces a stopped node's bundle with a release, converts its store to format 5, checks readiness and identity, and restores the previous bundle and store when a step after the stop fails. `deployment/scripts/roll-to-format5.md` describes its preparation; it is rehearsed on copies of both production stores.

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.7` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit. The macOS desktop app is not in this release; the 1.1.6 desktop app is on the v1.1.6 release.

## Updating an installed node

- **From 1.1.4, 1.1.5 or 1.1.6,** run `spacedatanetwork update install`. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The command fetches the signed update and verifies it against the bundle's update root; a helper then stops the running node, swaps the bundle, starts the node and waits for it to answer ready. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Replacing the binary by hand works as before: stop the node, install the 1.1.7 download or package in place of the old one (keep `keys/` and the config), and start the node. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **From 1.1.0 or earlier,** update by hand, because the updater in those releases reverts the updates it drives itself: stop the node, install the 1.1.7 download or package in place of the old binary (keep `keys/` and the config), and start the node. A format-4 store converts at the first start; the v1.1.4 release notes give the disk it needs and how long it takes.
- **The first start** compiles the new storage engine once, about a minute and a half on a 4-CPU machine; `spacedatanetwork prewarm-aot` does that before the restart.

## Linux key password file

A fresh node on Linux gets its key password file from the installers, the packages and the container, as since 1.1.5. The v1.1.5 release notes say where the file is kept for each kind of install and what a copy of the node's data opens.
