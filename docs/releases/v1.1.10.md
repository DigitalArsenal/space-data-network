# Space Data Network v1.1.10

Space Data Network 1.1.10 is the node as on `main` at the tag `v1.1.10`. It replaces v1.1.9 as the release to download.

## After this update a node imports only the lanes it subscribes to

`peers.trusted_import` and the five-minute shard catch-up are gone. Subscriptions are `$DSS` records (`subscriptions.dss`).

A node updated from 1.1.9 converts its lane ledger (`trusted-import-lanes.json`) and its `peers.trusted_import` allow list into subscriptions at its first start:
- each subscription comes from the trusted peer the lane's records came from, and starts at that peer's current batch;
- what was converted is recorded in `<storage.path>/trusted-import-converted`;
- the ledger and the config are left in place, and the converted subscriptions are kept where 1.1.9 does not read them. An update that rolls back to 1.1.9 therefore imports as 1.1.9 did, and reads no lane from its beginning.

Every start names each removed key still in the config, in the log and as the alert `subscription_conversion`. A new node whose config carries `peers.trusted_import` refuses to start. `docs/SUBSCRIPTIONS.md` has the commands, the first-read rules, the upgrade and the API.

## Compatibility

- **Publications:** a node on a build older than 1.1.6 does not accept publications signed by 1.1.6 or later, 1.1.10 included. Nodes that exchange publications must all run 1.1.6 or later.
- **Stores:** a store at store layout 2 (created by 1.1.9 or later, or promoted) opens only in 1.1.9 or later. This release does not change an existing store's layout or format. A store it creates opens in 1.1.9 again after a rollback.
- **Lane streams:**
  - A 1.1.9 producer answers the new lane statement (`read-chunk` with `PROJECTION` `STATEMENT`) with an error. A new subscription to it is refused; `--force --start beginning` follows it unsized. A converted subscription imports the lane's `$PNM` publications and waits to start its stream until the producer runs this release.
  - A 1.1.9 follower of a producer on this release keeps following.
- **Update status:** nodes of 1.1.9 and earlier drop the new update-status messages unread and do not relay them. In `update fleet` they show as `not reporting`.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. 1.1.4 through 1.1.10 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced.

## What is in it beyond 1.1.9

### Subscriptions are the only import gate

- **First reads are bounded.** No subscription is read from a lane's beginning unless it was made with `--start beginning`, or by the rule of a `keep-all` or `archive-all` lane after its size check.
  - A producer that refuses a saved cursor (a rebuilt index or store) gets the lane started again at its current batch, with the alert `follow_cursor_refused`.
  - On a lane whose history the node keeps, the records not read are kept with the subscription (`sync subscriptions`: "not read") until `sync subscribe --start beginning` reads the lane again, or `sync subscribe --acknowledge-unread` accepts the gap.
- **One shared reservation.** Each followed page, each fetch by content address of a current batch, and each `$PNM` publication import is checked before it is stored against one reservation that all lanes share. A lane stops, with its cursor kept, before the store would pass `subscriptions.record_ceiling` (default 32,000,000) or leave less than 1 GiB free under `storage.path` (alert `follow_stopped`). It resumes once the page fits.
- **Gossip stores nothing.** A record gossiped on a schema topic (`POST /api/v1/pubsub/publish`, the sdn-js `publish`) names no lane and is no longer stored by any node. Signed `$PNM` announcements are unchanged.
- **Commands.**
  - `spacedatanetwork sync subscribe --schema <standard> --provider-id <provider> --source-name <source> --from <producer peer id>` subscribes. It prints the producer's size of the first read, and the node refuses a read its free disk or record ceiling cannot take, unless `--force`.
  - `sync subscribe --from-ledger` plans the subscriptions of a 1.1.9 ledger and allow list, and makes them with `--yes`.
  - `sync unsubscribe` and `sync subscriptions` complete the set. `sync status` reads through a running daemon.
- **Stream limits.** A producer serves a peer it does not trust at most 8 followed streams, and 64 for all such peers. Peers in `peers.trusted_peers` get 16 streams, outside the 64.
- **Removed:** the feed-head announcements and their topic, the trust-promotion catch-up, the `$DSS` `Sync` action and `security.require_signed_feed_heads`.

### Updates

- **Nodes no longer all restart for an update at the same moment.** A node acts on an update it accepted at its own time within `update.rollout_window_seconds` (default 1800, 30 minutes; `0` acts at once; at most 86400).
  - The delay is fixed by the node's peer ID and the update ID, and is kept in `updates/pending.json` across a restart.
  - `update check` and `status` print `update_pending=<id> ... due_at=<time>`.
  - The release signer can sign a window into the signal, which replaces the node's setting for that update.
  - `update.max_delay_seconds` is replaced by `update.rollout_window_seconds`.
  - `update install` typed on a node still installs at once.
- **`spacedatanetwork update fleet` shows which version every node runs.** Each node publishes its own update status on its channel's update topic, signed by its peer key: its version, a pending update and when it acts, the last failure and whether it was rolled back, and the newest signal it accepted.
  - The status travels as one SDS `$UST` record (SDS 1.292.0), not JSON.
  - `--json` and `GET /api/peers/versions` (administrators only) give the same data. `update.publish_status: false` publishes none.
- **An interrupted home install still leaves the new build on trial,** and a build that passed its trial is never tried again.
- **`update install --config <the node's config>` works while the node runs,** including behind an origin certificate the system does not trust.

### Publication

- **A catalog row can list several products of different standards.** A paired catalog (`catalog_product_source`) publishes rows that list, for example, a GP `$OMM`, an SGP4-XP `$OCM` and an SDN-AP record side by side.
  - Each product resolves among the records of its own standard: retain one product source per standard the rows name (`OCM.fbs`, `OMM.fbs` and `MOR.fbs`). `$MOR` is the minimum orbit record of the catalog builder's minimum profile.
  - A snapshot publishes one series per product standard (OCM, then OMM, then MOR), then the index.
  - A generation admits four products per object (one per CAT product kind), and a closure of up to 400,000 product references.
  - See `sdn-server/docs/catalog-publication.md`.
- **A snapshot guard keeps a short pull from replacing a whole catalog.** A snapshot lane can set `min_record_ratio` (against the newest published series) and `min_records` (an absolute floor) under `publishing.retention.lanes[]`. A batch under the higher of the two is refused:
  - nothing is exported, pinned or announced, and the lane keeps advertising the catalog it had;
  - the batch stays in the store;
  - the node logs one `snapshot guard: ... REFUSED` line.
  - Unset (the default) keeps the old behavior. See `sdn-server/docs/snapshot-guard.md`.
- **IPNS pointers reach readers when the DHT put does not finish.** `publishing.ipns_pointers[]` takes three options, all off by default:
  - `delegated_publishers`: the node reads back the record Kubo signed, checks it against the name, and sends it to each Routing V1 publisher, such as `https://delegated-ipfs.dev`;
  - `republish_every`: re-signs and re-sends the current pointer while no newer series replaces it;
  - and a minute after boot, it re-sends the record Kubo holds.
  - A re-signed record of the same value counts as newer, so the republish and the resume send it. See `sdn-server/docs/ipns-pointers.md`.
- **A published lane can be withdrawn in one step.** `POST /api/v1/admin/dataset-updates/retract?schema=<standard>&providerId=<provider>&sourceName=<lane>` (loopback only) is a dry run unless `apply=true`. It retires every series, advertised row and pin of the lane, deletes the lane's records, and refuses to publish it again. Followers that read the producer's `lane_retracted` remove the lane's records they hold from that producer.

### Engine and runtime

- **A flow that fetches from no publisher no longer backs off after a quiet run.** The flow scheduler treated a clean run of any flow that stores records but landed no batch as a failed retrieval. It doubled the flow's window (up to 24 h) and skipped timers in the same slot. A flow whose declared capabilities are all local (clock, storage query, ingest and write, timers, context, crypto) now counts a clean run as a success, whatever it stored. The catalog builder's partition flows, which tick every 10 minutes, are an example: before this, the build advanced only right after a restart. Retrieval flows are unchanged.

- **An idle node uses far less CPU.** FlatSQL 3.12.14 runs its file-size and quota passes only when the store's files have changed (at least once a minute), and waits a second after a pass ends before the next one. Each pass opens every type's files. Its idle writers, lanes and indexers sleep on their doorbells instead of polling.
  - On a launchd agent at background priority, an idle node used about 25 % of a core on 1.1.9's engine and about 2 % on this one.
  - Store format 5 and layout 2 are unchanged.
- **A rare crash of a Linux node is fixed.** The WebAssembly runtime detached threads that were already running. In glibc through at least 2.42 (sourceware bug 19951), detaching a thread that is exiting at that moment can read freed memory, and the node ended with a segmentation fault; every supported Linux host was exposed. The runtime now starts these threads detached and links compiled code on one thread. `spacedatanetwork substrate-selftest` reports `patch_series` (10).
- **`peers.enable_dht: false` now means no DHT at all.** The embedded Kubo routes nothing (routing `none`). Before, the setting left a DHT client with no bootstrap peers. That client learned the public DHT through any connected peer that serves it, and dialed the peers it found: a node meant to stay private, connected only to its own peers, joined the public DHT through them. Nodes with the DHT on are unchanged.
- **A node whose bond is not attested backs off.** It refreshes its bond attestation at growing intervals up to once an hour, instead of every 10 seconds.
- **SDS 1.292.0** throughout the node.

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.10` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit.

## Updating an installed node

- **From 1.1.4 through 1.1.9,** run `spacedatanetwork update install`, or let the node take the release from its channel within its rollout window. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **The first start converts the import settings** (above). Read `sync subscriptions` afterwards. A lane the conversion could not tie to a producer is named in `trusted-import-converted`.
- **A node that cannot write its install folder** updates itself into its home folder from 1.1.9.
- **From 1.1.0 or earlier,** update by hand: stop the node, install the 1.1.10 download or package in place of the old binary (keep `keys/` and the config), and start the node.
- **The first start compiles the new storage engine once.** It takes about a minute and a half on a 4-CPU machine, and longer on a background-priority service. `spacedatanetwork prewarm-aot` does it before the restart.
