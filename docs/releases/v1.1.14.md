# Space Data Network v1.1.14

Space Data Network 1.1.14 is the node as on `main` at the tag `v1.1.14`. It replaces v1.1.13 as the release to download.

## An update's restart no longer cuts a dataset publication short

Before it stops for an update the node finishes the publications that are running, for at most 30 minutes, and refuses new ones meanwhile; `spacedatanetwork status` prints `update_stop_wait=` while it waits. A publication refused because the node is stopping, for an update or any other stop, answers HTTP 503 with `Retry-After` (it answered 400). A lane or batch publication that a stop or a crash ends anyway, or that was refused while the node stopped, is published again once the next start is ready, unless it is older than 24 hours or, on a snapshot lane (`snapshot_batches`), its lane has published another batch since it was requested (checked again once the publication holds its lane). On any other lane, whose batches are parts each published once, every marked part is published again, oldest first. It is tried at most 3 times across starts, then reported failed, and the lane's alert stays raised until the batch is published. An interrupted one is first reported as failed at the step "interrupted by the node's stop", which raises the lane's `publication_failed` alert until it completes, so an operator's restart during a publication raises the alert for the minutes the publication takes again. The update helper waits that much longer for the daemon to exit, adding at most one hour to its stop grace whatever the daemon states.

The update that installs 1.1.14 is itself stopped by the earlier build, which does not wait: a publication running at that moment is cut short as before. Updates from 1.1.14 on wait.

## A manual run is no longer cut off when its command stops waiting

`spacedatanetwork apps run` gave up after about 65 seconds ("daemon unavailable") and the node then cancelled the run ("context canceled"), so a flow that needed longer never finished by hand. A manual run now belongs to the node: it runs to its end whatever the command does, within a bound (the flow service's `execution_timeout`, or 2 hours, including any wait for its `exclusive_group`). The node's stop cancels it and answers a request waiting for it at once. The command waits and says every 30 s that the run is still going; `--timeout <duration>` bounds the wait (the command then prints how to see the result and exits non-zero, and the run continues), `--detach` returns at once, Ctrl-C stops waiting (the run continues; `--cancel-on-interrupt` cancels it instead). The new `apps status <app-id> [trigger-id]` shows a run's state and result, and `apps cancel <app-id> [trigger-id]` cancels a running one; a cancelled run gives back its attempt in the provider's minimum interval, so the next manual run starts at once. A second `apps run` of a schedule that is running joins that run; `--force` does not apply to a run started without it, and the command says so. `apps run` follows its own run by id: when the node no longer knows it (a restart), the command says so and exits non-zero instead of reporting another run. Scripts use the same route: `POST .../schedules/<trigger-id>/run?detach=1`, then `GET ...?id=<id>`; `DELETE ...?id=<id>` cancels that run (404 when it is not the one running, so a cancel never ends another run), `DELETE` with no id cancels whichever runs. `apps run --cancel-on-interrupt` cancels its own run only. The dashboard's Run now waits for the run as before; a page closed meanwhile no longer cancels it.

## A publication alert is decided from the store, clears when its batch is published or gone, and survives a restart

A `publication_failed` alert of a batch cleared only when that same batch was published, and a restart dropped it whether or not anything was published. The node now records each failed scope in the store and decides from the store when it clears. A failed batch clears when a completed publication of the whole batch exported the set it holds now (equal fingerprints), or when the batch holds no records any more (a replace-current lane superseded them, they expired, or the lane was retracted). A publication of another batch never clears it: if every record of a failed batch also sits in other, published batches, the alert still stays until that batch is published whole or its records go, and publishing the batch whole clears it. The batch is checked at each of its failures, after each completed publication of the whole batch, when a supersede or an expiry removes records of its lane, and at start once the node answers ready; a check costs one fingerprint of the failed batch, whatever the size of the lane. A completed publication of the whole batch clears it when it is reported; the check after it raises the alert again when records arrived in the batch while that publication ran. A retraction of the lane clears every failed scope of the lane. A batch the snapshot guard refused says what clears it (a newer batch superseding it, or the guard no longer refusing it) instead of advising a publication the guard refuses again. A failed head of a batch or of the lane, a failed publication of the whole lane, a failed announcement of existing publications, and a failed batch of a datastore lane clear when the same operation completes again; a publication of a head never clears a failed batch. The windows a publication wrote before it failed partway are never taken for a publication of the batch and are not announced again by an announcement of existing publications. At most 16 failed batches are tracked per lane; beyond them the alert says so and stays until a publication of the whole lane completes.

## Retention releases the windows of a failed publication

Node 1.1.11 and earlier adopted the windows a publication wrote before it failed (rows, pins and the announcements already sent) as a series of their batch at the lane's next completed publication, and kept them like any other series. They are now marked unfinished when written and never adopted, so the lane's retention (`publishing.retention` with `keep_series` set) retires their rows and unpins their shard, index and manifest CIDs at the lane's next completed publication, as it does for any row no series names. With `keep_series: 0` nothing is released, as before. A subscriber that fetched such a window from its announcement keeps its copy; the producer no longer serves it once retention released it. Windows an earlier release already adopted stay adopted.

**Rollback.** 1.1.13 and earlier do not read the marks an interrupted publication leaves in `publication-runs/` in the publication folder, and do not publish it again; a mark is read again when the node runs 1.1.14, within its 24 hours. They do not read the store's record of failed scopes or of unfinished windows either: a `publication_failed` alert is dropped by their restart, and the windows of a failed publication are adopted as a series of their batch at the lane's next completed publication, as before 1.1.14.
