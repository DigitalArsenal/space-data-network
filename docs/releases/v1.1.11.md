# Space Data Network v1.1.11

Space Data Network 1.1.11 is the node as on `main` at the tag `v1.1.11`. It replaces v1.1.10 as the release to download.

## A followed lane can keep its publications, and a node with its DHT off reaches the producers it follows

Since 1.1.10 a followed lane's records arrive on its stream. While the stream holds the producer's current batch, the lane's publications (the producer's signed manifests, shards and indexes) are not fetched. Two things then went wrong on a gateway host, whose readers fetch a producer's publications from it:

- it held none of the newest publications. On 2026-11-21 the SpaceAware console read "the provider node no longer holds the published files" for each new space-weather batch;
- with its DHT off it could not fetch them either. Kubo's Bitswap asks only peers that served blocks before, LAN peers and peered peers, so a producer the node was merely connected to was never asked.

This release fixes both:

- **`sync subscribe --publications keep`** fetches and imports every publication of the lane again, as 1.1.9 did. The lane's retention rule decides which publications stay (`replace-current` keeps the current batch's).
  - On a lane already followed it changes only that; the stream and its cursor stay. The stored-`$PNM` catch-up then reads at once the publications it had passed over.
  - `--publications stream` turns it off.
  - `sync subscriptions` shows the lane with "publications: kept" (`keep_publications` in `--json`).
  - The API is `POST /api/v1/sync?publications=keep|stream`.
- **A node with `peers.enable_dht: false` peers each producer it follows a lane from** in Kubo's peering service when the followed stream opens, and removes it once no lane is followed from that producer. A producer in the Kubo repository's `Peering.Peers` is left as it is; `swarm/peering/ls` lists them. Nodes with the DHT on are unchanged.

`docs/SUBSCRIPTIONS.md` has the details.

## Compatibility

- **Rollback to 1.1.10:** a subscription that keeps its publications carries `publications=keep` in its `SYNC_FILTER`. 1.1.10 does not know that field, so it holds such a subscription without running it (alert `subscription_refused`) until the node runs 1.1.11 again. The node's other subscriptions run.
- **Publications:** a node on a build older than 1.1.6 does not accept publications signed by 1.1.6 or later, 1.1.11 included.
- **Stores:** unchanged from 1.1.10 (store format 5, layout 2).

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. 1.1.4 through 1.1.11 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced.

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.11` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit.

## Updating an installed node

- **From 1.1.4 through 1.1.10,** run `spacedatanetwork update install`, or let the node take the release from its channel within its rollout window. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **From 1.1.4 through 1.1.9,** read the v1.1.10 notes first: the first start of 1.1.10 or later converts the import settings into subscriptions.
- **From 1.1.0 or earlier,** update by hand: stop the node, install the 1.1.11 download or package in place of the old binary (keep `keys/` and the config), and start the node.
