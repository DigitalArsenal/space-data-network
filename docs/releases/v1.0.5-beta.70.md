# Space Data Network v1.0.5-beta.70

The macOS app opens by double-click. Every release before this one was
ad-hoc signed and unnotarized, so Gatekeeper refused it with "Apple could not
verify this app is free of malware" — a dialog whose only buttons are Move to
Trash and Done. That is fixed, and the rest of this release is the other half
of beta.69's promise that a binary reports its own build, plus the defects that
only appear when you install what was actually published and run it.

## What changed

- **The macOS app is signed and notarized.** It carries a Developer ID
  signature and a stapled notarization ticket, so it opens normally and
  validates offline — a first launch with no network still works. Previously
  the app was ad-hoc signed: `codesign` called it valid, and Gatekeeper
  rejected it anyway, because Gatekeeper asks whether an app is notarized, not
  whether it is signed. If a build signs but cannot be notarized, the release
  now fails rather than shipping something that looks fixed and is blocked
  identically.

- **The container reports the release it was cut from.** v1.0.5-beta.69's
  published image answered `spacedatanetwork/1.0.5` on `/api/v1/version` and,
  more importantly, on libp2p identify, while the same release's tarball binary
  answered `spacedatanetwork/1.0.5-beta.69`. The release stamp reaches the Go
  binary through an ldflag; the Dockerfile has always accepted it and the
  workflow that builds the published image passed it on neither of its two
  build legs, so every container node on the network was indistinguishable
  from a dev build and from every other release. Both legs now pass it, and the
  build fails if `docker run <image> version` disagrees with the tag.

- **`sdn --version` works.** It answered `Error: unknown flag: --version`.
  `--version` and `-v` now print exactly what `sdn version` prints, from one
  place so the two cannot drift.

- **Apple Silicon no longer updates itself onto the Intel build.** The
  `latest-mac.yml` in v1.0.5-beta.69 listed only the x64 files while the
  release carried arm64 ones. electron-updater reads one channel file per
  platform and chooses the architecture from inside it, so an Apple Silicon
  install would have taken the x64 build under Rosetta on every update. The two
  macOS legs build on different runners, and each one's channel file was
  overwriting the other's; they are now merged, and a feed with no arm64 entry
  fails the release.

- **The node reports the FlatSQL engine it actually runs.** The suite manifest
  named flatsql 1.4.5 while the embedded engine artifact is built from 2.0.3 —
  its recorded source commit and sha256 match the bytes on disk. The manifest
  described a version the node has never run.

- **The `docker run` line on the front page works.** It named
  `dockerdigitalarsenal/space-data-network:1.0.5-beta.69`, and the registry
  holds `v1.0.5-beta.69` and `beta` and no such tag, so copying it gave
  "manifest unknown". The docs sync now forces the tag spelling and checks
  every tag the site names against the registry's real tag list.

- **A fresh node's first boot is not three red errors.** A stock node logged
  `ERROR … celestrak-gp-ingest skipped: flow is not installed` three times.
  That skip is the designed path — the default config declares those services
  so an operator can enable them by installing the bundle — and it now says so
  at `Info`.

- **Nodes offer webtransport.** The transport had been registered since it was
  written and no config ever declared a listen address for it, so the
  webtransport half of a browser's two unrelayed routes to a node was dead
  code. The new address shares the QUIC port, so no additional port is opened.

- **sdn-js is on one libp2p major again.** The browser client had been
  bridging libp2p 1.x and 3.x through shims; it now runs a single current
  major (libp2p 3, kad-dht 16, circuit-relay-v2 4, noise 17, yamux 8, helia 7)
  with the shims deleted and no WebCrypto dependency — ed25519 is reimplemented
  over @noble/curves and verified byte-identical to upstream. `npm audit`
  reports no vulnerabilities in the production closure.

- **INSTALL.md stopped misinforming Windows readers.** It said the desktop app
  was macOS-only in this beta; it ships for Windows and Linux too. Its Docker
  filename template also expanded to a 404 — the container asset spells the
  version with dots, not the tag's hyphen.

- **The runtime image drops libsqlite3.** A leftover from before the FlatSQL
  migration: nothing in the image links it, and the daemon needs only libm and
  libc.

## Verification added

A real browser now dials a real node. Headless Chromium loads the published
browser bundle over http, brings up a node inside the page, and completes a
request and response against a live go-libp2p host over webtransport,
webrtc-direct and websockets. The page counts constructions of `WebTransport`
and `RTCPeerConnection` — neither exists outside a browser — so each case
proves which transport carried its bytes rather than only that bytes arrived.

The existing interop test runs under Node over a websocket and could not have
told you any of that: a browser has no TCP, and both direct transports are
built on APIs Node does not have and on certificate-hash authentication only a
browser enforces.

## Still unsigned on Windows

Windows binaries carry no Authenticode certificate, so SmartScreen shows
"Windows protected your PC" — choose More info, then Run anyway. If you
downloaded the bundle with a browser, clear its mark-of-the-web before
expanding it (`Unblock-File` on the .zip) or the extracted exe may refuse to
start. docs/INSTALL.md covers both.

## Note for operators

`sdn.spaceaware.io` announces only websocket addresses — nginx terminates TLS
on 443 and proxies the websocket to the node, and nginx cannot front the UDP
transports. Browsers reach it over `wss` today. Offering the direct transports
in production is a deployment change, not a client one.
