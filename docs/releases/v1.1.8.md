# Space Data Network v1.1.8

Space Data Network 1.1.8 is the node as on `main` at the tag `v1.1.8`. It replaces v1.1.7 as the release to download.

## Compatibility: nodes that exchange publications update together

**A node on a build older than 1.1.6 does not accept publications signed by 1.1.6 or later, 1.1.8 included.** The signed dataset manifest names its index as a PublicationState file (`*.index.fb`), and the signed feed-head frame carries two more columns; an older node refuses both. Nodes that exchange publications must all run 1.1.6 or later: update them together.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. A node with default settings acts on update signals it hears on the network. A signal signed with that key can make such a node download and run a program from any HTTPS address. 1.1.4 through 1.1.8 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced.

## What is in it beyond 1.1.7

- **A dataset publication outlives the request that started it.** A flow publishes a batch by asking the node's own publish route, and that request was cut off at five minutes. The publication stopped with it, after writing its shard and index but before its manifest, its record and its announcement, nothing was logged, and the flow run still reported success. A node with large lanes had published nothing new since 2026-11-01 for this reason. A publication now runs to its end whatever its client does: it waits at most one hour for its lane and runs at most one hour once it holds the lane. A second request for a publication that is running waits for that run's answer instead of starting another one. A publication that completed is answered as a success.
- **The node's own publish route is exempt from the five-minute cap for flows.** A flow's request to the publish route on the node's own admin listener waits for the publication's bounds plus a minute, is not paced as outgoing traffic and does not follow a redirect. Every other request a flow makes keeps the five-minute cap. The publish route also clears the admin server's ten-minute write limit for its own answer, so an answer that comes later still reaches the flow.
- **A failed publication is seen.** It is logged as an error with its lane, batch and the step that failed (export, pinning, signing, the record, the announcement and the rest), and it raises the alert `publication_failed` for its lane. The alert clears once the failed batch is published, or the whole lane for a publication without a batch; a publication of another batch, an empty one or a request to announce an existing publication does not clear it. A flow run whose publish request fails or is refused ends with an error instead of success.
- **Publications stop with the node.** Stopping the node cancels every running publication, refuses new ones and waits up to ten seconds for them, before the store closes. A publication ended this way is logged as stopped with the node and raises no alert.
- **Publication files no record points to are removed**, at the start of the node and after each completed publication, together with the temporary files of writes that never completed. Files of a publication that is running are kept, and so are the files of a schema with no publication record at all (a moved or restored store). The one-hour age guard on this cleanup is gone.
- **Datastore publications have their own folder**, `dataset-publications/datastores/<datastore>/<schema>/`. **Effect on an updated node:** datastore publication files written in the old layout, under `dataset-publications/<schema>/`, are removed at the first start, as files no node record points to. No reader could find them: a publication's files are looked up in the store that holds its record, and a datastore's records live in the datastore. Their pinned copies in IPFS are not touched.
- **A batch publication reads only its batch.** The plan of a batch publication read the whole lane from its start and kept the batch's records; it now reads from the batch's newest record down and stops at the batch's count, and reads the whole lane only when the lane's counters do not describe the batch exactly. The newest 30,000-record batch of a 2,010,000-record `$OMM` lane: plan read 82 ms and 78 ms against 686 ms and 672 ms, and the publish answered in 917 ms and 737 ms against 1.549 s and 1.343 s; the engine no longer logs a slow scan of 2,000,384 rows for it.
- **Two settings for tests.** `SDN_ADMIN_WRITE_TIMEOUT` (a duration) sets the admin server's write limit in place of ten minutes, and `SDN_HTTP_REQUEST_MAX_TIMEOUT` (a duration below five minutes) lowers the cap on a flow's other outgoing requests. Neither is needed on a production node.

The storage engine and the store format are those of 1.1.7 (FlatSQL 3.12.10).

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.8` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit. The macOS desktop app is not in this release; the 1.1.6 desktop app is on the v1.1.6 release.

## Updating an installed node

- **From 1.1.4, 1.1.5, 1.1.6 or 1.1.7,** run `spacedatanetwork update install`. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The command fetches the signed update and verifies it against the bundle's update root; a helper then stops the running node, swaps the bundle, starts the node and waits for it to answer ready. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Replacing the binary by hand works as before: stop the node, install the 1.1.8 download or package in place of the old one (keep `keys/` and the config), and start the node. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **From 1.1.0 or earlier,** update by hand, because the updater in those releases reverts the updates it drives itself: stop the node, install the 1.1.8 download or package in place of the old binary (keep `keys/` and the config), and start the node. A format-4 store converts at the first start; the v1.1.4 release notes give the disk it needs and how long it takes.
- **From 1.1.6 or earlier, the first start** compiles the storage engine once, about a minute and a half on a 4-CPU machine; `spacedatanetwork prewarm-aot` does that before the restart.

## Linux key password file

A fresh node on Linux gets its key password file from the installers, the packages and the container, as since 1.1.5. The v1.1.5 release notes say where the file is kept for each kind of install and what a copy of the node's data opens.
