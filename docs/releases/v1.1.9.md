# Space Data Network v1.1.9

Space Data Network 1.1.9 is the node as on `main` at the tag `v1.1.9`. It replaces v1.1.8 as the release to download.

## Compatibility: nodes that exchange publications update together

**A node on a build older than 1.1.6 does not accept publications signed by 1.1.6 or later, 1.1.9 included.** The signed dataset manifest names its index as a PublicationState file (`*.index.fb`), and the signed feed-head frame carries two more columns; an older node refuses both. Nodes that exchange publications must all run 1.1.6 or later: update them together.

## Compatibility: a store 1.1.9 creates does not open in 1.1.8 or earlier

**A store this release creates, and a store it is told to promote, opens only in 1.1.9 or later.** Such a store is at store layout 2; 1.1.8 and every earlier release open only layout 1, and the update channel refuses to install or roll back to a build that cannot open the store. An existing store is not changed by the update: it stays at layout 1 and opens in 1.1.8 again after a rollback.

## Security: install 1.1.4 or later

Every release up to and including 1.1.0, and the container images tagged `1.1.1` and `v1.1.1`, trust one update-signing key, `d4a971a7e534`, and that key is compromised. A node with default settings acts on update signals it hears on the network. A signal signed with that key can make such a node download and run a program from any HTTPS address. 1.1.4 through 1.1.9 trust only the update key `12cb25de07c0` and refuse the old one wherever it appears. The v1.1.4 release notes say what to do on a node that cannot be replaced.

## What is in it beyond 1.1.8

- **No SQL record window on new stores.** SQL on a store saw only a window of each standard's records: the newest 10,000, or 400,000 for `$OMM` and `$TBS`. A store created by this release (an empty data folder) sees every record of every standard: it is created at store layout 2 with unlimited SQL visibility, with `storage.unlimited_sql_visibility` unset. **An existing store keeps its windows when the node updates;** it is never promoted by default. `storage.unlimited_sql_visibility: true` promotes it, once and for good: back the store up first; from then on `false` refuses to start and removing the setting keeps the store unlimited. `false` keeps a store bounded. Every limit on a query (rows, bytes, results, time, memory) still applies, and running out of one is an error, never a shorter answer. `spacedatanetwork status --config <config>` and `spacedatanetwork store-migrate --store <data> --status` print the store's format and layout, the latter without opening the engine or changing a file. `sdn-server/docs/sql-visibility.md` has the details.
- **No silent empty or short answers.** A query of the raw record stream that names a standard with no SQL relation (one the node does not register, a CID-only or field-sealed standard, an unknown source) is an error naming the relation instead of an empty answer; a registered standard with no records still answers empty. `GET /api/v1/pubsub/messages` still answers at most 10,000 records, and now marks the page truncated (QRP `TRUNCATED`, status partial) when more are stored. A standard whose field the node seals at rest is one an extraction rule reads is left unregistered on every store: the node starts, logs a warning naming the standard, the field and the rule, refuses every write to it, and lists it in `status` and `store-migrate --status` (`store_unregistered_standards`; `none` for the embedded standards).
- **FlatSQL 3.12.12.** It contains 3.12.11: a lane of more than 8,388,608 records no longer ends the engine during a checkpoint. On a node with a large catalog lane this had failed `$MPE` publications. The engine now keeps 24 bytes per record for this in place of 56, in blocks, and reads the rest of each record's digest back from the store when it needs it. **Cost:** after a restart the cache rebuild re-reads each unit's digests (a lane's commit root took about 45 to 50 % longer from a fresh cache on a 606,000-record store, native; a fresh replay of 2 million records took 9 % longer). About 32 million records across all lanes fit in one engine's 2 GiB heap. Commit roots are unchanged.
- **A node updates itself without root and without a service account.** A node whose account cannot write its install folder (a bundle unpacked under `/opt` by root and run by a system service as an ordinary account) could not update itself: every update was staged in, and swapped into, that folder, and failed there. Such a node now fetches, verifies and installs updates under the home folder of its account, in `~/.spacedatanetwork/bundle/<key>`, one folder per install, or in `<storage.path>/update-bundle/<key>` when there is no usable home folder (none, a missing one, or one the account cannot enter, as under the shipped systemd unit's `ProtectHome=true`; the log says so). It never changes the install folder, the service unit or the installed files. It does this by signal, by feed check and with `update install`, and needs no update helper: the daemon installs the build while it serves, stops its services and starts again through the installed path in the same process. The installed build verifies the new build against its own update roots (its signed manifest, its signed archive and every one of its files) and starts it as a trial with a deadline of `update.health_timeout_seconds`; a trial that is not ready by then, or that crashes, is rolled back to the previous build and kept aside under `updates/failed/`. A service restart or a reboot during a trial runs the trial again, at most three times. A build that was changed, is not signed, is older than the installed build, or that another account can change is refused with `update: the build under <folder> is refused: <why>; running the installed build`, and the installed build runs. Root never runs a build from a home folder, and one install serves one node per account. A node that can write its install folder updates it in place through the helper, as before. Windows needs a writable install folder.
- **`service install --dry-run`** prints the service file and commands without writing or running them.

**Downloads.** Installers and archives for macOS, Linux and Windows, the container image `dockerdigitalarsenal/space-data-network:v1.1.9` (linux/amd64 and linux/arm64), the signed update feed and their checksums are attached to this release. Every platform is built from the tagged commit. The macOS desktop app is not in this release; the 1.1.6 desktop app is on the v1.1.6 release.

## Updating an installed node

- **From 1.1.4 through 1.1.8,** run `spacedatanetwork update install`. The release channel at `https://sdn.spaceaware.io/updates` serves this release. The command fetches the signed update and verifies it against the bundle's update root; a helper then stops the running node, swaps the bundle, starts the node and waits for it to answer ready. The node keeps its identity and its data, and the replaced build is kept as a rollback slot. Replacing the binary by hand works as before: stop the node, install the 1.1.9 download or package in place of the old one (keep `keys/` and the config), and start the node. Desktop, package, VM-bundle and container installs do not update themselves: install the new release.
- **A node that cannot write its install folder** cannot update itself from an earlier release into this one: install 1.1.9 by hand once. Later releases reach it through its home folder.
- **From 1.1.0 or earlier,** update by hand, because the updater in those releases reverts the updates it drives itself: stop the node, install the 1.1.9 download or package in place of the old binary (keep `keys/` and the config), and start the node. A format-4 store converts at the first start; the v1.1.4 release notes give the disk it needs and how long it takes.
- **The first start** compiles the new storage engine once, about a minute and a half on a 4-CPU machine; `spacedatanetwork prewarm-aot` does that before the restart.

## Linux key password file

A fresh node on Linux gets its key password file from the installers, the packages and the container, as since 1.1.5. The v1.1.5 release notes say where the file is kept for each kind of install and what a copy of the node's data opens.
